Beethoven Engine Reference

Architectural rationale, prompt template grammar, and execution invariants.

1. What is Beethoven?

Project Beethoven is a sophisticated, bare-metal AI orchestrator and agentic harness written in C++20.

Unlike tools that aim to be "lightweight" Python or Node.js scripts passing strings back and forth, Beethoven takes the opposite approach: it is a heavy-duty, high-performance execution scaffold designed specifically for local language models (LLMs) running on consumer hardware (7B to 14B parameters).

Core Philosophy

Aggressively offload cognitive burden from the LLM into deterministic C++ code, so the model only has to do the part that actually requires intelligence.

2. The Core Problem: The Blind Worker

First-generation AI coding agents are heavily optimized for frontier cloud models (GPT-4, Claude 3.5 Sonnet). When pointed at a 12B model running on local hardware:

  • Context Evaporation: Over long context windows, a local model forgets whether it is on Windows or Linux, inventing invalid paths, hallucinating non-existent shell flags, and mangling syntax.
  • The Blind Worker Trap: When asked to write a function without exact AST context, a 12B model wastes thousands of precious tokens guessing what the surrounding structs, dependencies, or class signatures look like.
  • Silent Swallowed Failures: In sequential scripts, syntax errors are only discovered after the entire multi-minute workflow has executed.

3. The Three-Valued Split

The entire Beethoven harness is built around an uncompromising three-valued rule:

  1. Structure is C++'s: Whether a plan can run at all — whether the files it names exist, whether two tasks change one symbol at once, whether a dependency finishes before the task that needs it — is decided by code, from the plan and the AST, with no English read and no model asked.
  2. Meaning is the model's: What a goal asks for, what a symbol should do, which file a change belongs in — these are readings of a sentence, and the model decides them. C++ never overrules that reading with a regex.
  3. Facts are gathered by C++ and consumed by the model: The workspace tree, symbol outlines, imports, and compiler commands are gathered deterministically by the harness and injected into prompts verbatim.

4. Contract-First Composition

Rather than asking a worker LLM to arbitrarily generate code, Beethoven enforces top-down architecture. An Orchestrator LLM acts as lead architect, emitting a strict JSON blueprint:

  • One task per unit of work.
  • Each task explicitly names its target file, scope, dependencies, and behavioral contract.
  • The behavior travels with the task and reaches the worker verbatim.

Three conditions represent immediate refusals where the plan cannot run:

1. task %d names %s, which is not in the project and no task creates it
2. task %d recreates %s, which task %d deleted
3. the validation command names %s, which is not in the project and no task creates it

5. In-Memory Tree-Sitter AST Resolution

Beethoven maintains an in-memory graph of the workspace using Tree-Sitter C++ bindings. When a worker is dispatched:

  • The target file is parsed directly into an AST node tree.
  • Exact byte boundaries for function signatures, class members, and dependencies are sliced out.
  • The worker prompt receives the exact code slices rather than entire multi-thousand-line files, drastically saving context window tokens.

6. Parallel Tasks with Safe Splicing

Work is decomposed into scoped tasks executed concurrently across native threads (std::jthread). When multiple tasks modify different functions within the same file:

  • The tasks serialize execution order within the wave.
  • A real-time byte-offset tracker monitors length changes produced by earlier edits.
  • Subsequent patches automatically adjust their target offsets before splicing, eliminating merge conflicts completely.

7. Shadow Compiler Validation Loop

Code isn't just written; it is verified. Before any worker's edit is committed to the workspace tree:

  • The candidate bytes are written to an in-memory shadow buffer.
  • The harness invokes the language's declared verification adapter (e.g. clang++ -fsyntax-only, tsc --noEmit, cargo check).
  • If compilation fails, stderr diagnostics are captured and fed directly back into an immediate repair loop. The worker fixes errors while still holding context.

8. Dynamic XML Prompt Tag Specification

Beethoven prompt templates live in files/prompts/ as standard Markdown files with custom XML block tags (<bvn-*>).

Prompt Body Hygiene: All metadata tags are stripped before the prompt reaches the LLM. The model never sees metadata tags, ensuring zero wasted tokens.

<bvn-compose> <extensions>.cpp .cc .cxx .h .hpp</extensions> <runner>cmake --build --preset ci-linux</runner> </bvn-compose> <bvn-section id="writing" agents="worker"> Follow modern C++20 conventions: std::span, concepts, and RAII. </bvn-section>

9. CMake Presets

CMakePresets.json is the single source of truth for all builds:

  • dev / dev-linux: Everything enabled with Dear ImGui desktop workbench and voice pipelines (-O2 -g).
  • ci-linux: Orchestration engine only (headless). Warnings are fatal (-Werror).
  • asan: AddressSanitizer + UndefinedBehaviorSanitizer instrumentation.
  • bench: Maximum optimizations (-O3 + LTO). Used strictly for performance benchmarks.

10. Invariant Lint Gates

Beethoven enforces four hard source-level gates that run as ordinary ctest tests to guarantee architectural invariants never rot:

  1. check_layer_rule: Enforces that ai/llm remains transport-only, and core/validation never depend on ai/*.
  2. check_empty_catch: Prevents silently swallowed C++ exceptions.
  3. check_voice_locks: Enforces lock ordering discipline across real-time audio threads.
  4. check_hang_path: Verifies that failover hang breach paths stay 100% lock-free and allocation-free.
