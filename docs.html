How Beethoven works.

This page is the curated reference. Everything on it is checked against the engine repository, and the live section at the bottom renders the repository’s own documents on load so they cannot drift from the code.

Overview

Beethoven is a C++20 agentic harness for local language models, with a Dear ImGui desktop workbench, an in-process voice pipeline, and an HTTP/WebSocket serve mode. Most agents are Node or Python scripts passing strings to a frontier model. Beethoven is the opposite: a heavy, concurrent engine whose job is to take everything that does not require intelligence away from the model, so that a 7B–31B model on consumer hardware only has to do the part that does.

The core loop for a goal:

  1. The planner sizes the goal and, for large ones, writes a specification series first.
  2. The orchestrator emits a JSON blueprint: tasks, files, scopes, dependencies, behaviour.
  3. C++ checks the blueprint’s structure against the workspace tree and sends findings back, at most three times.
  4. Workers run in parallel waves. Each gets the exact symbol slices it needs and its task’s behaviour verbatim.
  5. Every edit is validated in a shadow copy by the checker its language declares, and repaired on the worker’s own turn.
  6. Edits are spliced into the tree with byte-offset tracking, then the project’s own test command runs over the whole tree.

The three-valued split

One rule runs the harness. Three kinds of decision, one owner each.

  • Structure is C++’s. Whether a plan can run at all is decided by code from the plan and the tree. No English is read and no model is asked.
  • Meaning is the model’s. What a goal asks for, what a symbol should do, which file a change belongs in. C++ never overrules that reading with a regex.
  • Facts are gathered by C++ and consumed by the model. The tree, the outline, the imports, the runner this machine actually has. The harness finds them and puts them in the prompt.
The model spends its tokens deciding, not discovering.

Blueprints and the structure check

The orchestrator emits one task per unit of work. Each task names its target file, its scope (symbol, file or module), its dependencies, and in its own words the behaviour the task must deliver. That behaviour travels with the task and reaches the worker verbatim; there is no shared table of contracts keyed by symbol.

C++ checks the plan’s structure against a fixed list. Each line is the exact sentence the planner is shown. Three are refusals: the run stops once the planner has been told and answers with the same finding.

task %d names %s, which is not in the project and no task creates it
task %d recreates %s, which task %d deleted
the validation command names %s, which is not in the project and no task creates it

The rest are facts the planner must account for. It fixes the plan or says why the plan is right, and its answer stands:

task %d names symbol %s in %s; %s is where the project defines it today
task %d writes %s; nothing else in this project has that extension
tasks %d and %d both change %s in %s in generation %d; the second starts from the first's result -- one task, or say why two
task %d is in generation %d and depends on task %d in generation %d; a dependency has to finish first
task %d names %s, which task %d changes in generation %d; task %d runs in generation %d
task %d edits %s, which goal_files does not list
task %d changes %s, a test that existed before the run; say why in seed_tests_touched or drop the task
task %d deletes %s; say in definitions whether its definitions are moved by this plan or removed from the project

Tasks that share a file inside one generation run one after another, each from the file as the one before left it. Inside a wave, a task that names a symbol runs after the task that changes it. A finding goes back to the planner in its own words, three asks at most for the whole plan, and a line the planner has not yet seen always earns its own ask.

Symbol slicing

Beethoven maintains a live Tree-sitter graph of the workspace. When a worker is dispatched to modify a symbol, the engine parses the target file into an AST, extracts the exact byte boundaries of the symbol and of the signatures and dependent headers it uses, and injects those slices verbatim. The worker never sees an entire multi-thousand-line file and never guesses a signature.

The interactive demo on the home page runs the same Tree-sitter C++ grammar in WebAssembly against one file so you can see the shape of what a worker is handed.

Parallel tasks and safe splicing

Goals are decomposed into isolated tasks that run concurrently on native threads. When several tasks target the same file, those tasks are serialised within the wave while a byte-offset tracker follows the length changes earlier edits produced. Each later patch adjusts its target offsets before splicing, so two workers editing two functions in one file never conflict.

Validation adapters

A worker’s edit is checked before it lands, against the file validators its own language declares. A language file says how a file of its kind is checked; the harness runs that check over the candidate bytes in the worker’s shadow copy and hands the diagnostics back on the worker’s own turn, while it still holds the file.

No tool name and no language name is written in the C++. Which checker a project has, how it is spelled on this machine, what its exit codes mean and which lines of its output name a failure are all declared rows in the language file. A language whose file declares no check falls back to the grammar already parsing it for symbol anchors and asks where the parse errors are. When nothing is declared, nothing is claimed, and the run says so instead of guessing.

Once every task has landed, the project’s own test command runs over the whole tree. A failure there is always a code error worth a repair round.

Prompt files and tags

Every prompt lives under files/prompts/ as Markdown with custom <bvn-*> block tags. Metadata tags are stripped during indexing, so the model never sees them. Sections are selected per role and per tag from SQLite, not injected as whole files.

files/prompts/
├── languages/      one file per language tag (107 today), plus _default.en.md
├── frameworks/     django, flask, laravel, nextjs, rails, react, spring-boot, vue
├── integrations/   CLI and tool integrations
├── environments/   host OS and container guidance
├── system/         agent role and persistent-mode prompts
├── task_types/     one-call task contracts (compose, repair, worker_v2, …)
└── snippets/       reusable fragments

A language file is the whole declaration of one language. Read top to bottom:

  1. <bvn-aliases>: the names the language answers to.
  2. <bvn-compose>: its facts. Extensions, manifests, import grammar, test runner, ignore dirs.
  3. <bvn-section> blocks: the conventions models read, per agent and per dialect tag.
  4. <bvn-validate>: how a file of this language is checked.
  5. <bvn-tool>: the language’s tools, with platform remaps and alternate spellings.
  6. <bvn-report> and <bvn-report-style>: how one line of checker output is read, and what a run’s exit codes and failure markers mean.
<bvn-aliases>c++, cplusplus</bvn-aliases>

<bvn-compose>
  <extensions>cpp, cc, cxx, hpp, hh, hxx</extensions>
  <accepts>c</accepts>
  <entry-points>main.cpp, src/main.cpp</entry-points>
  <indent unit="space" width="2" />
  <header-for from="cpp, cc, cxx" to="hpp" />
  <include-form>#include "{path}"</include-form>
</bvn-compose>

<bvn-section id="writing" agents="worker">
  Follow modern C++20 conventions: std::span, concepts, and RAII.
</bvn-section>

Child files such as h.en.md or cc.en.md declare no facts of their own; they carry <bvn-validate inherit="c" /> and whatever sections differ. The full grammar is in the repository’s docs/prompt_specification.md, rendered below.

Persistent memory

An embedded SQLite store tracks environment facts, project quirks and past corrections across sessions. At the start of a session the harness queries it and injects the relevant facts into the orchestrator’s prompt, so the model stops rediscovering that a project uses make, not cmake. The workbench has a memory inspector tab.

Voice

Speech-to-text and text-to-speech run inside the binary through sherpa-onnx on ONNX Runtime. The default STT model is Whisper tiny.en; TTS is Kokoro, with Piper voices and Kitten as alternatives, all fetched on demand from a catalog of checksummed models. Push-to-talk is bound to F8.

Barge-in works through speakers, not only headphones. A role arbiter fuses four sensors to decide who is talking: the playback state of the output sink, mic voice activity, a self-voice fingerprint against the agent’s persona, and an echo check of the mic transcript against the sentence just synthesised. Lock ordering across the real-time audio threads is enforced by a ctest gate.

A small in-process chat companion, Qwen2.5 0.5B in INT4 ONNX, runs on the same runtime for instant local chat and falls back to the configured coding model when its weights are absent.

Serve and connect

Run the engine headless on the machine with the GPU and attach a workbench from another. Serve mode is HTTP plus WebSocket on one listen socket, port 7420 by default, bound to loopback unless you say otherwise. Authentication is a shared token, compared in constant time. TLS is a certificate and key pair away.

beethoven --serve --bind 0.0.0.0 --port 7420 --auth-token "$BVN_SERVE_TOKEN" --tls-cert cert.pem --tls-key key.pem
beethoven --connect wss://gpu-box:7420 --auth-token "$BVN_SERVE_TOKEN"

Twenty-six RPC methods are on the wire today: file tree and read, symbol search and outline, diagnostics, diff list, approve and reject, job list, command dispatch, memory and prompt inspection. A phone portal that lets you approve a diff from your pocket is designed in the repository’s plans folder and not yet built.

Toolchain and presets

There is no global compiler requirement. On Windows the installer provisions a private MSYS2/MinGW64 toolchain outside the repository, at %LOCALAPPDATA%\beethoven\msys64 by default or wherever BVN_MSYS64 points. On Debian-family Linux it installs the apt packages it needs. Either way, git clean -xdf cannot destroy the toolchain.

./install.sh            # or install.bat from cmd.exe
./build.sh beethoven    # the main executable
./build.sh test         # build and run the whole suite in parallel
./build.sh test_reasoning_loop && ./build/windows/test_reasoning_loop.exe

CMakePresets.json is the source of truth:

PresetWhat it is for
dev / dev-linuxEverything on, -O2 -g. What the build scripts use by default.
ci-linuxOrchestration engine only, no GUI, no voice, warnings fatal.
ci-windowsFull MSYS2/MinGW build, warnings fatal.
asanAddressSanitizer and UBSan over the engine slice. Linux only.
bench-O3 plus LTO. The only preset to measure with.

Warnings are on and clean: -Wall -Wextra plus -Wshadow, -Wcast-qual, -Wnon-virtual-dtor and -Woverloaded-virtual, attached to first-party targets only. Dependencies are pinned to commits or hashes.

Lint gates

Beyond the GoogleTest suites, four source-level gates run as ordinary ctest tests and in CI. Each self-tests its own matcher on synthetic fixtures before reporting, because a gate that cannot fire is decoration.

GateInvariant
check_layer_ruleai/llm stays transport-only; core and validation never include ai/*; dissolved headers never come back.
check_empty_catchNo silently swallowed exceptions. A deliberately silent handler must carry an expected: comment saying why.
check_voice_locksLock ordering discipline across the real-time audio threads.
check_hang_pathThe watchdog’s hang-breach path stays allocation-free and lock-free.

CLI

The usage text, as the binary prints it.

Usage: beethoven [OPTIONS] [compose <goal>] [plan <goal>]

  (no command)           Launch interactive GUI
  compose [--decide] [--fresh] <goal>
                         Run the orchestrator pipeline (batch mode)
  plan "<goal>" [--dry-run] [--fresh | --revise]
  plan --dump            Size the goal, and when it leaves architectural
                         decisions open, write a specification series under
                         docs/plan/. --dry-run stops after the tree call and
                         costs 1 call on a small goal, 2 on any other;
                         --fresh replaces an existing plan (planner-origin
                         docs only); --revise folds this goal into it;
                         --dump prints the indexed plan as JSON and exits,
                         with no model call.
                         --probe <slot-or-heading> runs the ladder,
                         the questionnaire and the tree call as a
                         normal run does, then asks ONLY that chapter
                         of the first document -- a slot like 3.11 or
                         a heading fold like manifest or
                         file-manifest -- and writes nothing.
  --serve                Run as a headless workspace server (HTTP + WebSocket)
  --connect <url>        Connect a GUI client to a running server

Options:
  --interactive          Attach in-process GUI (default with no command;
                         with --serve: detachable view, engine keeps running)
  --project-root <path>  Root directory of the codebase (default: .)
  --api-endpoint <url>   LLM API base URL (default: config.ini setting or Ollama)
  --max-retries <n>      Max self-healing attempts (default: 3)
  --workers <n>          Max concurrent worker threads (default: CPU core count)
  --log-file <path>      Redirect log output to file
  --config <path>        Config file path (default: <resource_dir>/config.ini)
  --verbose              Enable DEBUG level logging
  --bind <addr>          Serve listen address (default: 127.0.0.1)
  --port <n>             Serve listen port (default: 7420)
  --auth-token <tok>     Shared by --serve and --connect (or BVN_SERVE_TOKEN)
  --tls-cert <path>      PEM certificate (requires --tls-key)
  --tls-key <path>       PEM private key (requires --tls-cert)
  --insecure             Allow non-loopback bind without TLS (discouraged)
  --help                 Show this help message

Exit codes: 0 clean; 3 hung worker at shutdown; 70 watchdog hang.

Repository layout

src/ai/          orchestrator, workers, chat, CSM, recovery, prompts, LLM transport
src/commander/   chat, compose and plan jobs, command routing
src/core/        engine bootstrap, state, VFS, watchdog, database, platform
src/net/         serve/connect, providers, transport
src/validation/  pluggable per-language compile/lint adapters
src/voice/       STT/TTS, analyzer, aligner, role arbiter
src/ui/          Dear ImGui workbench
src/workspace/   Tree-Sitter workspace graph and file splicing
files/prompts/   every sentence a model reads
docs/            architecture, prompt spec, TODOs
.agents/notes/   design plans, with landed dates and rejected hypotheses
